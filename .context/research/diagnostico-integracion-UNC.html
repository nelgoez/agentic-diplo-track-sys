1. Resumen Ejecutivo

Se realizó una auditoría técnica de las plataformas existentes de la UNC involucradas en el ecosistema de diplomaturas, mediante exploración automatizada con herramientas de testing de navegador (Playwright). El objetivo fue verificar la factibilidad técnica de integrar el sistema DTS con las plataformas existentes.

✅ Conclusión principal: La integración con Moodle es técnicamente viable desde hoy. La API REST de Moodle está operativa, se obtuvo un token de acceso funcional, y más de 200 funciones están disponibles para sincronización de estudiantes, cursos, completitud y calificaciones. No se requiere configuración adicional del lado de Moodle para comenzar.
⚠️ Atención requerida: El plugin de certificados (Custom Certificate) solo expone una función de borrado vía API. Para leer certificados emitidos de forma programática, se necesita exponer una función adicional de consulta. Alternativamente, puede usarse el estado de completitud de curso como indicador indirecto.
❌ Pendiente externo: La integración con SIU Guaraní depende de credenciales de API que debe proporcionar la DTI de la UNC. Sin ellas, la transmisión de notas y altas de diploma se implementará en modo simulado (mock) para demostración, con activación inmediata al recibir las credenciales.

2.1 Arquitectura de plataformas

Las plataformas de la UNC están auto-contenidas: el portal público (campusvirtual.unc.edu.ar, WordPress) actúa como vidriera informativa y de marketing, y en su barra de navegación ofrece un botón "Acceder" que conduce directamente a la página de login del LMS (campus.aulavirtual.unc.edu.ar/login/index.php, Moodle). Esta verificación se realizó mediante navegación automatizada (Playwright) confirmando el flujo completo: Portal WordPress → clic en "Acceder" → Login de Moodle.

⚠️ Corrección importante (verificado 29/05 19:33): El token de API Moodle obtenido es de tipo estudiante (servicio moodle_mobile_app, usuario nelthor). Este token solo permite consultar los datos del propio usuario. Para sincronización multi-estudiante en producción, la UNC debe proporcionar un token de administrador/site-manager de Moodle. Se verificó mediante Playwright que core_user_get_users_by_field funciona para el email del dueño del token pero retorna vacío para otros usuarios. La arquitectura del código ya soporta ambos escenarios: funciona con el token actual para demo (un solo estudiante) y funcionará con token admin para producción (todos los estudiantes).
✅ Implicación para la integración: No existen dos sistemas desconectados. El ecosistema es un continuo donde el portal WordPress redirige al LMS Moodle. DTS solo necesita integrarse con Moodle para acceder a todos los datos de cursos, estudiantes y certificados. El portal WordPress no requiere integración alguna.

El ecosistema de cursos y diplomaturas de la UNC reside íntegramente en la instancia Moodle. No existe una plataforma Open edX separada: la URL edx.campusvirtual.unc.edu.ar redirige automáticamente al WordPress, y desde allí se accede a Moodle.

5. Sistema de Certificados

5.1 Plugin utilizado

La UNC utiliza el plugin Custom Certificate (mod_customcert) para emitir certificados de finalización de cursos. Se verificaron certificados de dos tipos:

TipoCódigoCursoFecha de emisión
Certificado de Asistencia0B2ucYIk3pIA y automatización de flujos de trabajo27/01/2026
Certificado de AprobaciónYRtctId1PxIA y automatización de flujos de trabajo27/01/2026

5.2 Limitación actual de la API

El plugin mod_customcert solo expone delete_issue a través de la API REST del servicio móvil. Las funciones de consulta (get_certificates, get_issues) no están disponibles para consumo externo.

5.3 Soluciones propuestas

  1. Solución inmediata (sin acción de UNC): Usar core_completion_get_course_completion_status como indicador indirecto. Si un curso está "completado", DTS asume que existe un certificado. Esta solución funciona para todas las funcionalidades del motor de reglas y habilitación.
  2. Solución completa (requiere 5 min del admin Moodle): Crear un Web Service custom en Moodle que exponga mod_customcert_get_issues. Esto permite leer metadatos completos del certificado (código, fecha exacta, tipo). La configuración se realiza desde Site administration → Plugins → Web services → External services.

7.6 Fase B — Moodle Connection Real (completada 29/05/2026)

Se reemplazó el servicio mock de Moodle por llamadas reales a la API REST. El servicio ahora:

  1. Busca al estudiante en Moodle por email usando core_user_get_users_by_field
  2. Obtiene los cursos en los que está inscripto con core_enrol_get_users_courses
  3. Verifica la completitud de cada curso con core_completion_get_course_completion_status
  4. Genera certificados para cursos con estado "completado"
  5. Hace UPSERT en la tabla certificates de DTS con clave (student_id, course_id)

8. Integración con SIU Guaraní

Estado: La API REST de Guaraní 3.x está documentada (documentacion.siu.edu.ar) y expone servicios para consulta de estudiantes, registro de notas y emisión de diplomas vía SIDCer. La UNC utiliza Guaraní como sistema académico oficial.

8.1 Requisitos técnicos para la integración

  • Credenciales de API (usuario/contraseña configurado en servidor_usuarios.ini del módulo de gestión de Guaraní)
  • Acuerdo con la DTI de la UNC para habilitar el acceso externo a la API
  • Mapeo de campos: legajo/DNI del estudiante, notas de cursos, nota del módulo final, estado del diploma

8.2 Estrategia de implementación

  1. Mock funcional (inmediato): DTS incluirá un proveedor simulado de Guaraní que responde con datos de prueba realistas. Todo el flujo (sincronización de padrón → push de notas → alta de diploma) se implementa sobre el mock.
  2. Activación real (cuando DTI entregue credenciales): Cambiar un flag de configuración (providers.yaml) de active: mock a active: guarani para activar la integración real. Cero cambios de código necesarios.
